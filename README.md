# Чтение Евангелий — приложение совместного чтения до Рождества

Небольшое веб-приложение (PWA) для группы верующих: планы чтения Евангелий
с 19 октября по 25 декабря 2026 года, автоматическая фиксация факта прочтения,
заметки к стихам и доска лидеров.

Интерфейс на русском языке, рассчитан в первую очередь на телефон.
Текущая версия интерфейса — **1.5.0**. В разделе «Ещё» кнопка «Что нового»
раскрывает краткую историю обновлений (`client/src/releases.js`). Нумерация введена
с этим экраном: предыдущим выпускам присвоены 1.0.0 (`6416051`), 1.1.0 (`057ae18`)
и 1.2.0 (`9bc27ee`). При выпуске обновляйте историю и версию пакета клиента.
Доступны четыре плана: «Лайт» (30 записей), «Стандарт» (50), «Продвинутый» (50)
и «Хард» (68). В каждый план включён общий рождественский отрывок 25 декабря:
Лк 2:1–20 и Ин 1:14. Расписание и диапазоны стихов хранятся в `plans.json`.

## 1. Технологический стек и хостинг

**Стек:**

| Слой | Технология | Почему |
|---|---|---|
| Сервер | Node.js (≥ 22.5) + Express | простой API без лишних зависимостей |
| База данных | **SQLite** через встроенный `node:sqlite` | одна небольшая группа, файл на диске, без отдельного сервера БД и без нативных зависимостей |
| Аутентификация | случайный токен серверной сессии в `HttpOnly`-cookie, пароли — **bcrypt** (`bcryptjs`) | безопасное хранение, устойчивость сессии на устройстве |
| Клиент | React 18 + Vite + Bootstrap 5 | mobile-first SPA |
| PWA | `vite-plugin-pwa` (Workbox) | установка на экран телефона, офлайн-текст Библии |

Приложение — один процесс Node, который отдаёт и API, и собранный клиент, а состояние
держит в одном файле SQLite. Его можно развернуть на VPS или контейнерной платформе;
ниже приведена инструкция для текущего варианта — Railway:

- обычный VPS (запуск под `systemd` или `pm2`);
- контейнерные платформы (Docker-образ прилагается, `Dockerfile`);
- PaaS (Render, Railway, Fly.io и т. п.).

База — файл SQLite. Путь к ней и постоянное хранилище зависят от среды запуска:
локальный Docker Compose использует том `bible-data` в `/app/server/data`, а для
Railway ниже описан отдельный том `/data` с `DB_PATH=/data/app.db`. Не переносите
mount path из одной среды в другую без проверки содержимого каталога: монтирование
скрывает файлы образа в этой точке. HTTPS необходим для установки PWA и защищённых
cookie в продакшене; за обратным прокси задайте `NODE_ENV=production`.

### Деплой из GitHub на Railway

1. Отправьте исходный код в GitHub. Не добавляйте в репозиторий секреты, локальную
   базу SQLite или production-данные.
2. В Railway создайте проект через **Deploy from GitHub repo**, подключите аккаунт
   GitHub и выберите репозиторий. Railway соберёт приложение по корневому
   `Dockerfile`.
3. В настройках сервиса выберите production-ветку (например, `main`) и включите
   автоматический деплой новых коммитов из этой ветки.
4. До первого запуска подключите постоянный **Volume** с mount path `/data` и
   задайте переменные:

| Переменная | Значение |
|---|---|
| `NODE_ENV` | `production` |
| `DB_PATH` | `/data/app.db` |
| `SESSION_SECRET` | длинное случайное уникальное значение; хранить в Railway Variables, не в GitHub |
| `ADMIN_LOGIN` | выбранный вами production-логин администратора |
| `ADMIN_PASSWORD` | новый сильный production-пароль; не использовать локальный `admin123` |
| `APP_TIMEZONE` | `Europe/Belgrade` (или часовой пояс группы) |

Не задавайте на Railway `TEST_PLAN_START`: production использует даты из `plans.json`.
После успешного деплоя сгенерируйте публичный домен в настройках Networking сервиса;
Railway обслуживает его по HTTPS. `PORT` задаётся платформой автоматически.

**Production-база и учётная запись отличаются от локальных.** SQLite хранится в
`/data/app.db` на Railway Volume, а не в файловой системе контейнера или в GitHub.
Volume должен быть подключён именно к сервису приложения, а `DB_PATH` должен
указывать внутрь него. Не удаляйте и не пересоздавайте этот Volume при обычном
деплое: удаление Volume удаляет хранящиеся в нём данные. Деплой нового коммита
пересобирает контейнер, но не должен заменять подключённый Volume. Настройте и
периодически проверяйте резервные копии Volume отдельно.

Локальный Docker Compose намеренно подключает именованный том к `/app/server/data`:
при первом создании пустого Docker named volume Docker копирует в него файлы,
которые уже есть в этом каталоге образа, включая текст Библии. Том сохраняет это
содержимое и базу между перезапусками.

**Для Railway настройка другая:** не рассчитывайте, что новый Railway Volume,
подключённый к `/app/server/data`, заполнится файлами из образа. Подключённый том
скрывает содержимое каталога контейнера, в том числе встроенный текст Библии.
Поэтому в Railway используйте отдельный Volume в `/data` и `DB_PATH=/data/app.db`.
Не копируйте локальную базу в production автоматически и не удаляйте production
Volume или его данные.

Установите `ADMIN_LOGIN` и `ADMIN_PASSWORD` до первого запуска приложения с
production-базой. Bootstrap создаёт администратора только если такого логина ещё
нет. Если администратор уже существует, его пароль и сессии не меняются. Если логин
занят обычным пользователем, запуск завершается ошибкой — выберите другой
`ADMIN_LOGIN`. Повышение существующих пользователей не поддерживается.
Поэтому последующее изменение `ADMIN_PASSWORD` в Railway
не сбросит пароль существующей учётной записи. Для смены пароля используйте вход в
приложение и настройки учётной записи; не меняйте bootstrap-переменные в расчёте на
автоматический сброс.

Официальные инструкции Railway: [деплой GitHub-проекта](https://docs.railway.com/quick-start),
[автодеплой из ветки](https://docs.railway.com/guides/github-autodeploys) и
[постоянные Volumes](https://docs.railway.com/guides/volumes).

## 2. Текст Библии и лицензия

Используется **Синодальный перевод (1876)** — четыре Евангелия (Матфея, Марка, Луки,
Иоанна). Текст встроен в приложение (файл `server/data/bible/synodal.json`), внешних
запросов при чтении нет, текст доступен офлайн.

**Источник:** [getbible.net](https://api.getbible.net/v2/synodal.json) — перевод
«Synodal Translation (1876)». **Лицензия:** общественное достояние (текст 1876 года,
срок авторских прав истёк).

Импорт текста (выполнен один раз, повторно нужен только для пересборки данных):

```bash
cd server
npm run import-bible                 # скачает источник и запишет data/bible/synodal.json
# либо из локально скачанного файла:
npm run import-bible -- /путь/к/synodal.json
```

### Личные переводы

В «Ещё» можно выбрать перевод. Выбор хранится на устройстве отдельно для каждого
аккаунта; он меняет только отображаемый текст, не план, порог времени, прогресс,
баллы или привязку заметок и вопросов к стихам. По умолчанию — Синодальный.

Для личного изучения добавлены четыре Евангелия из предоставленных
файлов IBS Biblica, «Новый русский перевод (Biblica)» и EPUB «Современный русский перевод (РБО, 2011)». Файлы
`server/private-bible/ibs.json`, `biblica.json` и `rbo.json` исключены из Git и не входят в релизный
архив `git archive`; для согласованного production-релиза их нужно отдельно добавить
в `server/private-bible` чистого каталога релиза перед загрузкой на Railway. При
каждом следующем деплое сохраняйте эти файлы в пакете, иначе переводы исчезнут из
списка (прогресс останется). Базу SQLite в пакет релиза не копируйте. Docker при
локальной сборке включает их в образ. Если файла на сервере нет, соответствующий
перевод не предлагается, сохранённый выбор заменяется Синодальным.

Повторный импорт на macOS (передайте свои пути):

```bash
textutil -convert txt -output /tmp/ibs.txt '/путь/IBS Biblica.rtf'
python3 server/scripts/import-private-bibles.py /tmp/ibs.txt '/путь/РБО.epub'
textutil -convert html -output /tmp/biblica.html '/путь/Biblica. Современный перевод.rtf'
python3 server/scripts/import-biblica-html.py /tmp/biblica.html
docker compose up -d --build app
```

РБО RTF не используется из-за смешения текста со сносками. В EPUB тоже есть
дефекты распознавания: потерянные номера внутри абзацев сохранены объединёнными
диапазонами; отсутствующий отдельный текст обозначен явно. Текст одного перевода
не подменяется другим. Сноски EPUB не импортируются. Эти личные файлы не объявляются
общественным достоянием и не распространяются вместе с исходниками.

## 3. Запуск

Сервер сжимает файлы интерфейса при поддержке gzip браузером. Файлы `/assets/`
с хэшем в имени кэшируются на год (`immutable`); HTML и service worker проверяются
при обновлении. При локальном доступе по HTTP через IP service worker недоступен,
но обычный HTTP-кэш браузера работает.

### Разработка

Терминал 1 — сервер (порт 3000):

```bash
cd server
npm install
npm run dev
```

Терминал 2 — клиент (Vite, проксирует `/api` на сервер):

```bash
cd client
npm install
npm run icons      # при необходимости перегенерировать иконки
npm run dev
```

### Продакшен

```bash
# 1) собрать клиент
cd client && npm install && npm run build

# 2) запустить сервер (он отдаёт и API, и собранный клиент)
cd ../server && npm install
SESSION_SECRET=<случайная-строка> \
ADMIN_LOGIN=admin ADMIN_PASSWORD=<пароль> \
NODE_ENV=production \
npm start
```

Откройте `http://localhost:3000`.

### Docker Compose (рекомендуется)

```bash
docker compose up --build          # http://localhost:3000
docker compose down                # остановить
docker compose down -v             # остановить и удалить базу
```

`SESSION_SECRET`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `APP_TIMEZONE`, `TEST_PLAN_START`
берутся из окружения (см. `docker-compose.yml`), база сохраняется в томе `bible-data`.

### Docker (одиночный контейнер)

```bash
docker build -t bible-app .
docker run -p 3000:3000 \
  -e SESSION_SECRET=<случайная-строка> \
  -e ADMIN_LOGIN=admin -e ADMIN_PASSWORD=<пароль> \
  -v bible-data:/app/server/data \
  bible-app
```

### Тестовый режим: сдвиг дат плана

Для тестирования отображения статусов переменная `TEST_PLAN_START` сдвигает даты
всех планов так, чтобы первая запись приходилась на указанную дату. Это позволяет
проверять сценарии с прошедшими, текущими и будущими записями:

```bash
TEST_PLAN_START=2026-09-01 docker compose up --build  # первая запись — 1 сентября:
#   тогда сразу видны красные крестики, а прочитанное даёт синие/зелёные галочки
```

Для повторяемых тестов задавайте только **фиксированную дату** (`YYYY-MM-DD`). Не
используйте `TEST_PLAN_START=today`: значение будет сдвигаться при каждом запуске,
из-за чего сохранённый прогресс начнёт относиться к другим датам плана. В локальном
`docker-compose.yml` задана фиксированная тестовая дата `2026-10-18`; перед обычной
эксплуатацией удалите `TEST_PLAN_START` (в Railway её не задавайте), чтобы даты
брались из `plans.json`.

### Тесты

Автотесты на встроенном раннере Node (без зависимостей) — 48 тестов: статусы и граница
суток, подсчёт стихов и порог, а также интеграционные проверки API (регистрация,
блокировка, планы, зачёт чтения, приватность заметок, лайки, лидерборд, админка).

```bash
cd server && npm test                       # локально
docker compose run --rm test                # в контейнере
```

## 4. Первый администратор

Администратор создаётся при запуске из настроек развёртывания (переменные
`ADMIN_LOGIN` и `ADMIN_PASSWORD`): если пользователя с таким логином нет — он
создаётся с ролью `admin`. Существующий администратор остаётся без изменений;
если логин занят обычным пользователем, сервер не запускается и сообщает об ошибке.
Повышение существующих пользователей не поддерживается. Поэтому `ADMIN_PASSWORD`
служит для первоначального bootstrap, а не для сброса пароля при каждом запуске.

После первого успешного bootstrap ID администратора сохраняется в таблице
`bootstrap_admin`. Его переименование не создаёт новый аккаунт при перезапуске;
последующая смена bootstrap-переменных не создаёт другого первого администратора.

Альтернативно — из командной строки:

```bash
cd server
node scripts/create-admin.mjs <логин> <пароль>
```

Команда также создаёт только новый аккаунт: существующего администратора не меняет,
а при совпадении с логином обычного пользователя завершается с ошибкой.

Администратор умеет: видеть всех пользователей и их прогресс, **сбросить** пароль
(посмотреть старый невозможно — пароли хранятся только хэшем), удалять чужие
**открытые** заметки.

## 5. Правила входа и защита от перебора

- Пароль — не короче 3 символов (других ограничений нет).
- Логин уникален; при сравнении регистр и пробелы по краям игнорируются.
- В «Ещё» карандаш справа от логина включает редактирование, дискета сохраняет
  новое имя. Занятый или пустой логин не принимается. Аккаунт, прогресс, заметки и
  сессии сохраняются; при следующем входе нужно использовать новый логин.
- **Блокировка:** после **5** неудачных попыток подряд вход по этому логину
  блокируется на **15 минут**. Успешный вход сбрасывает счётчик; окно подсчёта — 60 минут.
- Пароль хранится только в виде хэша bcrypt.

Все указанные числа настраиваются через переменные окружения (см. ниже).

## 6. Конфигурация (переменные окружения)

Сервер читает настройки из окружения; значения по умолчанию заданы в
`server/src/config.js` (единая точка, легко заменяются).

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | порт сервера |
| `DB_PATH` | `server/data/app.db` | файл базы SQLite; задавайте путь внутри постоянного хранилища для выбранной среды (Railway: `/data/app.db`) |
| `SESSION_SECRET` | dev-значение | передаётся в `cookie-parser`; текущая сессионная cookie не подписывается, поэтому значение не влияет на проверку или отзыв сессий |
| `APP_TIMEZONE` | `Europe/Belgrade` | часовой пояс группы (граница суток) |
| `SESSION_DAYS` | `180` | срок жизни сессии на устройстве |
| `READING_MIN_SECONDS` | `0` | дополнительный минимум к порогу на стих |
| `READING_SECONDS_PER_VERSE` | `2` | секунд на каждый стих отрывка |
| `READING_IDLE_RESET` | `30` | секунд без активности сбрасывают «активность» |
| `READING_MAX_SECONDS_PER_REQUEST` | `60` | максимум секунд, принимаемых сервером за один запрос |
| `MIN_PASSWORD_LENGTH` | `3` | минимальная длина пароля |
| `AUTH_MAX_FAILED` | `5` | неудачных попыток до блокировки |
| `AUTH_LOCK_MINUTES` | `15` | длительность блокировки, минуты |
| `AUTH_ATTEMPT_WINDOW` | `60` | окно подсчёта неудач, минуты |
| `NOTE_MAX_LENGTH` | `2000` | лимит длины заметки |
| `ADMIN_LOGIN` / `ADMIN_PASSWORD` | — | первый администратор |
| `COOKIE_SECURE` | = `NODE_ENV==='production'` | флаг Secure у cookie; при HTTP по сети ставить `false` |
| `TEST_PLAN_START` | — | только для тестов: фиксированная дата `YYYY-MM-DD` сдвигает даты планов; не используйте `today` |
| `NODE_ENV` | — | `production` включает `secure` cookie |

Порог засчитывания чтения: `max(READING_MIN_SECONDS, READING_SECONDS_PER_VERSE × число стихов)`.
По умолчанию сервер и обратный таймер используют один порог: **2 секунды на стих**. «Отрывок
прочитан» показывается после достижения конца отрывка и подтверждения зачёта сервером.
При повторном открытии отрывка таймер возобновляется с накопленного сервером активного времени.
Стихи на экране чтения сгруппированы по главам; заметки к длинным текстам можно сворачивать.
В ленте открытых заметок нажатие на ссылку стиха раскрывает его текст прямо над
заметкой; повторное нажатие сворачивает текст.

## 7. Как работает зачёт чтения

**Ручной кнопки «прочитал» нет.** Чтение засчитывается технически:

- **клиент** копит активное время (секунды идут, только когда вкладка видима и была
  недавняя активность — прокрутка, касание, движение), отслеживает достижение
  последнего стиха и отправляет события `reading-progress` каждые 10–15 секунд, а
  также при сворачивании и закрытии страницы;
- **сервер** накапливает секунды по паре (пользователь, запись плана), клампит
  секунды за один запрос разумным максимумом (по умолчанию 60 с — иначе одним
  запросом можно зачесть всё) и зачитывает запись, когда выполнены оба условия:
  «дошёл до конца» и «набрано не меньше порога». Момент засчитывания (`readAt`)
  сохраняется один раз.

Статусы вычисляются сервером из фактов (без ночных заданий):

| Статус | Условие | Вид |
|---|---|---|
| Прочитано вовремя | `readAt` ≤ конца даты записи | зелёная галочка |
| Прочитано позже | `readAt` позже конца даты | синяя галочка |
| До начала участия | не прочитано, дата раньше дня выбора плана | пусто |
| Пропущено | не прочитано, сутки записи истекли | красный крестик |
| Сегодня/будущее | иначе | нейтрально |

Красный крестик становится синей галочкой при позднем чтении и зелёной уже не станет.
Дата начала участия — день выбора плана; при смене плана началом участия в новом плане
становится день смены (интерфейс показывает предупреждение), отметки хранятся отдельно
по каждому плану.

Доска лидеров и API `/api/leaderboard` доступны только авторизованным участникам.

**Баллы в рейтинге** начисляются за чтение и лайки: чтение в срок — **5 баллов**,
чтение с опозданием — **4 балла**, каждый лайк, полученный на заметку, — **1 балл**.
Пропущенные и не начатые записи баллов не дают. Баллы целые, дополнительное округление не применяется.

### Вопросы к стихам

Во время чтения можно задать публичный вопрос к стиху. Вопросы видны участникам на вкладке
«Вопросы»; ответы загружаются и отображаются только после раскрытия конкретного вопроса.
Автор может редактировать и удалять свои вопросы и ответы. Администратор может удалять чужие.
Текст вопроса и ответа ограничен настройкой `NOTE_MAX_LENGTH` (по умолчанию 2000 символов).
